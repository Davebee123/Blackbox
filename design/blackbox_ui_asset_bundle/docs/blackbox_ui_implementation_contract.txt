- illicit
- lived-in

- readable under pressure

==================================================
6. REVISED COMBAT MODEL UI CONTRACT
==================================================

The user has updated the underlying conceptual combat model.

Implement the UI around this logic:

- Viruses are composed of subsystems.
- There is no abstract separate Core target as the main gameplay focus.
- Virus Integrity represents total denaturation progress.
- Damaging subsystems reduces Virus Integrity.
- Destroying specific subsystems removes their behaviors.
- Specific loot is associated with breaking specific subsystems.
- Shell(s) can gate access to other systems.
- AoE attacks can denature the virus broadly but may reduce targeted subsystem-break opportunities.
- Precision attacks can break chosen systems and secure targeted loot.

UI CONSEQUENCES
- Virus Integrity remains visible as an aggregate “boss life” bar.
- The subsystem list is the actual functional anatomy.
- Active attack timing must be shown on subsystem rows.
- The player must be able to understand:
  - which subsystem is attacking
  - when it will attack
  - what it will affect
  - which subsystem is currently protected
  - which subsystem would yield loot if destroyed

==================================================
7. TIMING / TELEGRAPHING CONTRACT
==================================================

Remove dependence on a single distant cycle indicator.

The UI must communicate timing locally where it matters.

REQUIREMENTS
- Each active hostile subsystem shows its own timing information.
- Hostile action time remaining should live on the subsystem row in a right-side timer box.
- The active hostile subsystem row should be visually emphasized.
- The player’s currently cast/queued action must be shown in the dedicated YOUR ACTION panel.
- The player should not need to look in three different places to know:
  - what is attacking
  - how long until it lands
  - how long until their own action lands

SUBSYSTEM TIMER BOX
For each active hostile subsystem, show:
- remaining time, e.g. 0.8s / 2.1s / 4.7s
- timer box on far right of row
- red for hostile urgency when dangerous
- yellow/amber or neutral when not urgent

ABILITY CARDS
Bottom abilities should show:
- active cast progress if the selected/current action is being cast
- cooldown progress via darkened overlay / receding progress bar
- ready state clearly visible
- selected state highlighted

PLAYER ACTION PANEL
This is the primary place to watch the player’s own action progress.

Accent helper

GLOW RULES
- subtle amber panel glow only on active framed areas
- hostile systems receive restrained red emphasis
- selected states use controlled amber glow
- avoid overbloom
- no heavy neon cyan glow
- no full-screen haze

Suggested values:
- active amber glow: 0 0 14px rgba(246,197,75,.14)
- strong selected amber glow: 0 0 18px rgba(246,197,75,.22)
- hostile glow: 0 0 14px rgba(255,91,61,.18)

TYPOGRAPHY
Use:
- primary UI font: clean sans-serif with slightly condensed or technical feel
- command/ASCII/log font: monospace

Recommended implementation-friendly stack:
Primary:
- "Inter Tight", "Rajdhani", "IBM Plex Sans", system-ui, sans-serif
Monospace:
- "IBM Plex Mono", "JetBrains Mono", "Cascadia Mono", monospace

Typography use:
- Titles: bold/sans
- Labels: uppercase/sans
- Command prompt: mono
- Timer values: mono or bold sans
- Virus visual labels: mono acceptable
- Event list: sans for body, mono for timestamp optional

GRIME
- subtle scratches/noise texture
- worn panel edges
- distressed but legible
- terminal grit
- not broken
- not high-noise CRT
